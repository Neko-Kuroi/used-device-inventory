# 中古スマホ・PC 在庫管理プログラム 計画書

作成: 2026-11-21
位置づけ: Tshirt3 (Neko-Kuroi の在庫管理アプリ) のカスタム版ではない。
Tshirt3 からは「Flask + SQLite で小さく作り、テストで固める」という作り方だけを参考にする、別系統の新規プログラムとする。

## 1. 目的

中古のスマートフォンとパソコンの販売に向けて、1台ごとの状態と履歴を
正確に記録し、「今どの段階にあるか」「何を確認済みか」「いくらで仕入れ、
いくらで売れたか」を迷わず追える在庫台帳を作る。

公開向けの EC サイトではない。販売者側が内部で使う在庫管理が目的である。
（公開用の商品ページ出力は、必要になったら後段で別途検討する。）

## 2. いちばん大きな設計の違い: 数量在庫ではなく個体管理

- Tシャツの在庫: 同じ品番・色・サイズを「何枚あるか」で数える数量在庫。
- 中古スマホ・PC: 同じ機種でも1台ごとに傷、バッテリー、付属品、修理歴が違う。
  したがって在庫の単位は「機種」ではなく「個体 (シリアル番号で識別する1台)」。

この違いが全ての土台になる。個体を登録し、個体ごとに状態と履歴を持つ。

## 3. 土台 (Tshirt3 の作り方を踏襲する部分)

- Flask + Python 標準ライブラリの sqlite3 のみ。外部ライブラリは増やさない。
- 画面はサーバー側で描くテンプレート方式。API とフロントエンドの分離はしない。
- ログインとユーザー管理を持つ（必須）。
- 利用形態（2026-11-21 決定）: プログラムと DB はホストとなる1台の PC に置き、
  スマホ・タブレット・他の PC から Tailscale 経由で複数端末で使う。
  一般のインターネットには公開しない。
  帰結: ホスト PC が起動していないと他端末からは使えないこと、
  DB のバックアップをホスト以外にも取る運用にすること、を前提とする。
- 変更はすべて履歴に残す（いつ、誰が、何を変えたか）。
- 自動テストを最初から用意し、状態遷移と金額計算をテストで固定する。

## 4. 個体が持つ情報

### 4.1 共通
- 個体ID（内部連番）、シリアル番号
- 種別: スマートフォン / パソコン / タブレット（当面は前2つ）
- メーカー、機種名
- 状態ランク: S / A / B / C / ジャンクの5段階（2026-11-21 決定）。
  定義の目安（運用しながら微調整してよい）:
  S = 未使用に近い極美品、目立つ傷なし /
  A = 小さな傷はあるが目立たず、機能は全て正常 /
  B = 目立つ傷や使用感はあるが、機能は全て正常 /
  C = 目立つ傷に加え、実用に支障のない範囲の不具合がある /
  ジャンク = 動作不良がある。修理前提、部品取り、またはジャンクとして販売する
- 外観メモ: 傷・凹み・欠けの場所と程度（自由記述＋部位の選択肢）
- 付属品: 箱、ケーブル、充電器、説明書などの有無を項目ごとに記録
- 仕入れ: 日付、仕入れ先、仕入れ価格
- 販売: 予定価格、販売日、販売先（販売経路）、実売価格
- 保証: 保証期間（販売日から何日か）、返品・保証対応の記録
- データ消去: 消去した日時、方法、実施者（中古端末では必須の記録とする）
- 備考、登録者、作成・更新日時

### 4.2 スマートフォン固有
- 容量、メモリ、色
- バッテリー状態（最大容量 % が読める機種はその値）
- IMEI（判別できたものは記録する。2026-11-21 決定、補足同日。
  全文が見えるのは管理者の詳細画面だけとし、一覧では末尾4桁だけを表示する。
  CSV 出力にも全文は含めない。
  判別できない場合は無理に埋めず、空欄のまま記録なしとする。必須項目にはしない。
  その場合、ネットワーク利用制限の確認はできないので、確認結果は
  「確認できず」と記録する）
- SIM ロック / ネットワーク利用制限の確認結果
- アクティベーションロック解除の確認

### 4.3 パソコン固有
- CPU、メモリ、ストレージ（種類と容量）、GPU
- OS（種類とバージョン、ライセンス状態）
- バッテリーサイクル回数（ノートの場合）
- キーボード配列、光学ドライブ等の有無

## 5. 状態の流れ (ライフサイクル)

個体は次の段階を順に進む。飛ばしたり戻したりした場合は履歴に理由を残す。

1. 仕入済み（登録直後）
2. 検査中
3. 整備中（清掃、修理、部品交換、初期化・データ消去）
4. 販売可能
5. 取り置き（予約済み）
6. 販売済み
7. 返品・保証対応（販売済みからのみ）
8. 処分（ジャンク販売、部品取り、廃棄）

「販売可能」へ進める条件: 検査チェックリストが全項目完了し、
データ消去の記録があること。条件を満たさない個体は進められないよう
プログラム側で止める。

## 6. 検査チェックリスト

種別ごとに項目を用意し、個体ごとに合否と実施日時・実施者を記録する。

- スマホ例: 電源、画面表示とタッチ、カメラ（前後）、スピーカーとマイク、
  ボタン類、充電、Wi-Fi、モバイル通信、指紋・顔認証、バッテリー状態
- PC例: 電源と起動、画面、キーボード全キー、トラックパッド、カメラ、
  スピーカーとマイク、充電とバッテリー、Wi-Fi、有線 LAN、USB 等の端子、
  ストレージの健康状態

## 7. 金額の扱い

- 価格は自動計算しない。仕入れ価格と販売価格は人が決めて入力する。
  （状態ランクからの自動計算は、実績が溜まってから必要なら検討する。）
- 一覧で粗利（実売価格 − 仕入れ価格 − 経費の合計）が見えるようにする。
- 経費は全部入れる（2026-11-21 決定）。部品代、送料、販売手数料、その他
  その個体のために発生した費用を、項目ごとに（日付、種類、金額、備考）
  記録し、合計を粗利から引く。合計だけでなく内訳も見えるようにする。

## 8. 写真について

- 初版では写真アップロードは入れない。
  まずは台帳としての正確さを優先する。
- 必要性が高ければ後段で「正面・背面・傷」の定型写真を追加する。
  その際も保存形式と容量の上限を先に決める。

## 9. 作らないもの (初版の範囲外)

- 一般向け EC サイト、カート、オンライン決済
- 外部の認証サービスとの連携
- データベースの暗号化（シリアル番号等の扱いはアクセス制御で守る）
- 価格の自動計算

## 10. 進め方

- Phase 0: 本計画書の承認と未決事項の決定（完了、2026-11-21）
- Phase 1: 土台（ログイン、個体の登録・編集・一覧・検索、履歴）
  （完了、2026-11-21。テスト15件全合格、起動スモーク確認済み。
    実装は device_app/、使い方は README.md）
- Phase 2: 状態の流れと、販売可能への進行条件
  （完了、2026-11-21。テストは Phase 1 と合わせて24件全合格。
    状態は編集画面からは変えられず、詳細画面の専用操作でのみ変更する。
    戻す・飛ばす・返品・処分には理由が必須で、履歴に残る。
    販売可能ゲートは「検査完了＋データ消去記録＋利用制限が × でないこと」。
    検査完了は当面フラグで持ち、Phase 3 のチェックリストが全項目合格に
    なったときに自動で立つ形に置き換える。
    あわせて DB を v2 に拡張し、v1 の DB は起動時に自動で移行する）
- Phase 3: 検査チェックリストとデータ消去記録
  （完了、2026-11-22。テストは累計33件全合格。
    チェックリストは種別ごと: スマホ10項目、PC 11項目、タブレット8項目。
    結果は合格／不合格／対象外で、項目ごとに実施者と日時とメモを記録する。
    全項目に結果が入り不合格が無いときに検査完了となり、Phase 2 の
    販売可能ゲートと連動する。手動の検査完了フラグは廃止した。
    データ消去の記録には実施者も自動で残る。DB は v3 へ自動移行）
- Phase 4: 金額まわり（一覧での粗利、CSV 出力）
  （完了、2026-11-22。テストは累計41件全合格。
    経費は項目ごと（日付、種類＝部品代／送料／販売手数料／その他、金額、
    備考）に記録し、追加・削除は履歴に残る。粗利は
    実売価格 − 仕入れ価格 − 経費合計で、詳細と一覧に表示する。
    実売価格か仕入れ価格が無い個体は粗利を出さず「―」とする。
    販売予定価格での予定粗利も詳細に表示する。
    CSV 出力は一覧の絞り込みを反映し、IMEI は末尾4桁のみ
    （全文は出さない）。文字コードは Excel で開けるよう BOM つき UTF-8。
    DB は v4 へ自動移行）
- Phase 5: 仕上げ（使い方文書、テスト総点検、zip 化）
  （完了、2026-11-22。使い方文書 HOW_TO_USE.md を作成。
    テスト総点検: 本体41件全合格、まっさらなコピーでも41件全合格、
    実サーバーでの通しスモーク〈初期設定→登録→検査→販売可能→経費→CSV〉も合格。
    zip は ~/workspace/used-device-inventory.zip (20ファイル、約37KB)。
    展開したコピーでも41件全合格を確認。DB と secret_key は zip に含めない。
    これで本計画の Phase は全て完了。
    既知の制限: パスワード再設定の画面は無い。Satoru の手元での実行と
    Tailscale 経由の実運用は未確認）
- 完成後のレビュー修正（2026-11-22）: Satoru が zip を実地検証して挙げた
  指摘を、こちらでも全件再現確認のうえ修正した。決定は Satoru:
  関門の維持は併用方式（販売可能・取り置きの間は種別・IMEI・利用制限・
  データ消去の記録を編集ロック。検査で条件が崩れたら自動で検査中へ戻し
  履歴に残す）、返品時は検査結果とデータ消去の記録をリセット、
  種別変更時も検査結果をリセット。併せて、ログイン next の外部
  リダイレクト、「確認できず」の自動付与はスマホのみ、整備中→検査中も
  理由必須、登録時の消去実施者の記録、検索 LIKE の逃げ処理、
  CSV の式インジェクション対策、db.py の説明文を直した。
  テストは新規14件を追加して55件全合格、zip も作り直した。

各 Phase の終わりでテスト全合格を確認してから次へ進む。
